Performance در سایت سه‌بعدی؛ WebGL بدون قربانی‌کردن تجربه کاربر

تجربه سه‌بعدی خوب فقط زیبا نیست؛ باید روی دستگاه واقعی سریع، قابل تعامل و قابل کاهش باشد.

Rozhan Behrouzi۱۲ مهر ۱۴۰۵ROZNEX Insights

قبل از مدل‌سازی Performance budget تعریف کن

در وب سه‌بعدی، تصمیم‌های Performance باید قبل از ساخت Asset گرفته شوند. تعداد Polygon، اندازه Texture، تعداد Material، نور، Post-processing و رفتار دوربین همگی روی CPU، GPU و شبکه اثر دارند.

اگر Hero سه‌بعدی مهم‌ترین عنصر صفحه است، باید بدانیم روی موبایل چه چیزی واقعاً لازم است و چه چیزی می‌تواند کاهش پیدا کند یا با تصویر/ویدیو جایگزین شود.

همه چیز را در اولین Paint بارگذاری نکن

منابع پایین صفحه لازم نیست همزمان با محتوای بالای صفحه دانلود و پردازش شوند. web.dev برای Performance روی defer و lazy loading منابع غیرضروری تأکید دارد. همین اصل برای Texture، مدل ثانویه و بخش‌های تعاملی سه‌بعدی هم مهم است.

LCP را قربانی WebGL نکن

اگر Canvas یا Assetهای سه‌بعدی باعث شوند متن و تصویر اصلی دیر ظاهر شوند، Hero از نظر تجربه کاربر شکست خورده است. یک Poster سبک می‌تواند خیلی سریع نمایش داده شود و صحنه اصلی بعد از آماده‌شدن جای آن را بگیرد.

Fallback موبایل یک شکست نیست

کم‌کردن Geometry، خاموش‌کردن Post-processing یا استفاده از تجربه دوبعدی جایگزین در موبایل به معنی کم‌ارزش‌کردن پروژه نیست. هدف این است که داستان اصلی روی دستگاه واقعی کار کند.

Interaction باید Main Thread را قفل نکند

Pointer tracking، Scroll و انیمیشن‌های متعدد اگر بدون محدودیت اجرا شوند، Interaction را سنگین می‌کنند. کاربر باید بتواند Scroll، Tap و Navigation را بدون رقابت با Render loop انجام دهد.

اندازه‌گیری روی دستگاه واقعی

Performance سه‌بعدی را فقط روی لپ‌تاپ توسعه‌دهنده نسنج. حداقل یک گوشی میان‌رده، شبکه کندتر و حالت reduced motion را بررسی کن. Core Web Vitals هم باید در کنار FPS دیده شوند.

منابع: web.dev Performance و responsive design.

جمع‌بندی: تجربه سه‌بعدی حرفه‌ای آنی نیست که بیشترین افکت را داشته باشد؛ آنی است که در دستگاه واقعی، داستان را بدون قربانی‌کردن سرعت و تعامل منتقل کند.

برای مسیر اجرایی: طراحی سایت سه‌بعدی و تجربه تعاملی وب.
